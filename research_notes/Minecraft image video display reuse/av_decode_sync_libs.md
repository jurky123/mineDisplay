# AV Decode/Sync Libraries Reusable from a Fabric Client

## Which Java video decode options exist, and which run on Java 21/25, Windows/Linux/macOS (license + binary-size notes)?

### Takeaway
Only two decode paths are realistically embeddable in a Java 21/25 Fabric client mod today: JavaCPP/FFmpeg bindings (JavaCV or WaterMedia-style direct preset use, LGPL FFmpeg build) and pure-Java JCodec (permissive, no natives, but slow and H.264-main-profile-only); vlcj is GPL-3.0 and pinned to unreleased VLC 4, LavaPlayer is audio-only, and Xuggler/Humble-Video/GStreamer-Java-0.10 are dead or require a system install.

### Cited Findings
- JavaCV (org.bytedeco:javacv-platform, current 1.5.14) is a Java interface to OpenCV, FFmpeg and others via JavaCPP Presets, distributed via Maven Central with per-platform native jars; full `javacv-platform` pulls binaries for all platforms, and a single platform can be selected with `-Djavacpp.platform=` (e.g. `linux-x86_64`, `windows-x86_64`) — [Source](https://github.com/bytedeco/javacv)
- JavaCV requires Java SE 8 or newer (OpenJDK/Oracle/IBM/Microsoft), and 32-bit and 64-bit modules must not be mixed — [Source](https://github.com/bytedeco/javacv)
- JavaCPP Presets provide the FFmpeg module (currently FFmpeg 8.1.x, e.g. 8.1.1/8.1.2 with JavaCPP 1.5.14), offer both `ffmpeg-platform` (LGPL) and optional `ffmpeg-platform-gpl` ("almost everything enabled") artifacts, and the bundled `ffmpeg` executable can be extracted/embedded from Java — [Source](https://github.com/bytedeco/javacpp-presets/blob/master/ffmpeg/README.md)
- Most FFmpeg files are LGPL-2.1-or-later; optional parts and external libs (libx264, libx265, libxvid, frei0r, etc.) require `--enable-gpl` and flip the binary to GPL-2.0+; `--enable-nonfree` (e.g. FDK-AAC/OpenSSL combos) makes the binary unredistributable — [Source](https://github.com/FFmpeg/FFmpeg/blob/master/LICENSE.md); same matrix in FFmpeg legal docs — [Source](https://www.ffmpeg.org/legal.html)
- JCodec is a pure-Java (no natives) implementation of video/audio codecs under FreeBSD License; it supports H.264 main-profile decoder, H.264 baseline-profile encoder, VP8 I-frames-only, MPEG-1/2, ProRes, JPEG/PNG, MP4/MKV/MPEG-PS-TS demux, and is consumed as `org.jcodec:jcodec:0.2.5` on standard Java and Android — [Source](https://github.com/jcodec/jcodec)
- JCodec warns decoding is "typically an order of magnitude slower than native implementations (such as FFmpeg)", that H.264 encode quality/bitrate is much worse than x264, but decode quality should be bit-exact per spec — [Source](https://github.com/jcodec/jcodec)
- vlcj-5 requires LibVLC/VLC 4.0.0+ as a minimum (VLC 4.0 still in development/unreleased) and Java 11+; stable users are told to stay on the vlcj-4.x branch instead — [Source](https://github.com/caprica/vlcj/blob/master/README.md)
- vlcj framework itself is GPL-3.0-or-later (commercial license available on request), with JNA bindings split into a separate `vlcj-natives` project — [Source](https://github.com/caprica/vlcj/blob/master/README.md); libVLC itself is LGPL but VLC codecs carry MPEG patent/royalty caveats for the redistributor/end-user — [Source](https://docs.videolan.me/vlc-user/en/support/faq/legalconcerns.html)
- LavaPlayer (maintained fork `lavalink-devs/lavaplayer`, artifact `dev.arbjerg:lavaplayer`) requires Java 11+, is audio-only by design (outputs Opus frames for Discord bots), supports SoundCloud/Bandcamp/Vimeo/Twitch/local/HTTP plus MP3/FLAC/WAV/WebM-Matroska/MP4-M4A-AAC/OGG/M3U-PLS, and explicitly has no video track support — [Source](https://github.com/lavalink-devs/lavaplayer/blob/main/README.md)
- Xuggler is officially DEPRECATED in its README, which points users to Humble Video instead; it was LGPL (GPL if built against GPL FFmpeg) — [Source](https://github.com/artclarke/xuggle-xuggler)
- Humble Video (Xuggler successor) is AGPL-3.0 licensed, ships per-architecture native jars (`humble-video-arch-*`), and its platform list/JDK-1.6-era build (Vagrant/Chef, Mountain-Lion Mac) is stale/abandoned relative to Java 21/25 targets — [Source](https://github.com/artclarke/humble-video)
- GStreamer 1.x Java bindings (`gstreamer-java/gst1-java-core`, LGPL-3.0) are tested on Linux x86/Arm, Windows and macOS but require a separate system GStreamer install plus JNA, with releases via Maven Central under `org.freedesktop.gstreamer` — [Source](https://github.com/gstreamer-java/gst1-java-core)
- gst1-java-core's latest Maven Central release is dated Jan 14, 2021, and Swing/FX helpers are 2019-era; the old 0.10 `gstreamer-java` repo is archived UNMAINTAINED — [Source](https://mvnrepository.com/artifact/org.freedesktop.gstreamer/gst1-java-core); successor `org.java-gi:gstreamer` (LGPL-2.1, Java-GI generated) only has 0.13–1.0.0-RC releases in late 2025–2026 — [Source](https://mvnrepository.com/artifact/org.java-gi/gstreamer)
- GStreamer core/framework itself is LGPL (so apps can use any license), but patented/proprietary codec plugins can conflict with GPL apps — a documented reason to prefer permissive licensing for GStreamer-based apps — [Source](https://gstreamer.freedesktop.org/documentation/frequently-asked-questions/licensing.html)
- MCEF (Minecraft Chromium Embedded Framework, `CinemaMod/mcef`) is LGPL-2.1, embeds Chromium via java-cef/CEF (Chromium 116.0.5845.190 pinned in README), supports Win 10/11 x86_64+arm64, macOS 11+ Intel/Apple-Silicon, Linux glibc-2.31+ x86_64+arm64, downloads CEF binaries at runtime from `mcef-download.cinemamod.com`, and does not work on Android — [Source](https://github.com/CinemaMod/mcef)
- WaterMedia v3 (successor to WaterMedia 2.x/FancyVideo-API) uses FFmpeg plus house-made decoders, targets Java 17+, ships FFmpeg natives in a companion `WATERMeDIA: Binaries` jar so no system FFmpeg install is needed, and exposes GL/Vulkan/OpenAL engine abstractions — [Source](https://github.com/WaterMediaTeam/watermedia-v3)
- WaterMedia v3 Binaries support matrix is Windows x86_64 ✅, Linux x86_64 ✅, Linux aarch64 ✅, macOS x86_64/aarch64 ✅, Windows aarch64 ⛔, Android ⛔; the FFmpeg 8.1.2 native build is LGPL-3.0-or-later, built without `--enable-gpl`, x264 or x265 — [Source](https://github.com/WaterMediaTeam/watermedia-v3/blob/main/README.md)
- WaterMedia v2.x is Polyform-Strict-1.0.0 (non-commercial, no redistribution/derivatives) and v3 is Defensive-Public-Source-NC-1.0.0 (commercial use forbidden without contact); `WATERCoNFIG` is All-Rights-Reserved — so WaterMedia is a usage dependency, not reusable source — [Source](https://github.com/WaterMediaTeam/watermedia/blob/2.1.x/README.md); [Source](https://github.com/WaterMediaTeam/watermedia-v3/blob/main/README.md)

### Inferences
- For a Fabric mod on Java 21/25, JavaCPP FFmpeg presets are the only maintained native-decode path with all three desktop OSes and Arm Mac coverage; cost is jar size (tens of MB per platform; full platform aggregate is hundreds of MB) unless classifiers are narrowed per-distributable.
- LGPL FFmpeg builds (no `--enable-gpl`, no x264/x265 encoders) are the safe redistributable default; decoding H.264/H.265 with the built-in LGPL decoders does not itself flip the license to GPL, but shipping a `-gpl` preset build or linking GPL plugins would.
- vlcj and LavaPlayer should be excluded from video-decode shortlists (vlcj: GPL + VLC-4 unavailability + external player install; LavaPlayer: audio-only by design).
- JCodec is a legitimate zero-native fallback for thumbnails/short clips, not a main 1080p60 playback engine, given the documented order-of-magnitude slowdown and main-profile-only H.264 decode.

### Gaps
- No reliable 2026 source found for exact per-platform MB sizes of `ffmpeg-platform` 8.x classifiers or Java 25-specific certification; JavaCPP/preset CI builds claim Ubuntu-built Linux binaries work on most distros but size must be measured at pack time.
- No maintained pure-Java H.265/VP9/AV1 decoder suitable for realtime MC use was found; JCodec covers H.264/VP8-I-frames only.

## How do existing open-source MC-adjacent projects do synchronized playback (anchor timestamps, clock sync, HLS/DASH, pre-transcoded profiles)? Any reusable patterns?

### Takeaway
No MC project implements NTP-style clock discipline or HLS/DASH ABR in-engine; the reusable pattern is WaterMedia v3's authoritative server tick plus tiny fixed-size big-endian sync packets, FFmpeg-side pre-transcode to a single H.264 profile, and per-client MRL/platform resolvers — while browser-based mods (MCEF/CinemaMod/VideoPlayer) delegate all sync to Chromium/VLC and frame-sequence libs (FFmpegLib) avoid sync entirely.

### Cited Findings
- WaterMedia v3 provides `TxMediaPlayer` (texture/picture), `FFMediaPlayer` (FFmpeg full video/audio), and `ServerMediaPlayer`: "a headless wall-clock player that acts as the server-side time authority for synchronized playback" — [Source](https://github.com/WaterMediaTeam/watermedia-v3)
- WaterMedia v3 sync transport is "small fixed-size big-endian records in `org.watermedia.api.media.players.sync`, decoded by `Packet.of(ByteBuffer)`: Sync (29 B, the authoritative snapshot), Config (11 B), Watch/Unwatch (10 B), Report (20 B) and Control (19 B)"; apps implement one-method `send(ByteBuffer)` bridge and feed inbound bytes to `player.sync(payload)`, with `sync()` safe from the network thread and correction math on WaterMedia's own 50 ms tick, never the game thread — [Source](https://github.com/WaterMediaTeam/watermedia-v3)
- WaterMedia resource model is MRL (Multimedia Resource Location): connect to URL, resolve multimedia sources/quality variants/metadata, then open a `MediaPlayer` on a source index with GL/VK/AL engine suppliers (null disables that output) — [Source](https://github.com/WaterMediaTeam/watermedia-v3/blob/main/README.md)
- CinemaMod (watch-online-videos-together mod) is explicitly "NOT RELEASED, IN DEVELOPMENT" with blockers "convert to MCEF 2" and "remove the hard requirement for ffmpeg to be installed on the server" — i.e. browser playback + server ffmpeg pre-process, no custom clock protocol visible — [Source](https://github.com/CinemaMod/CinemaMod)
- VideoPlayer mod (NGoedix) plays videos in the GUI for all/specific players with volume/position/size controls and non-skippable modes (`/playvideo`, `/playgovideo`), but delegates actual decode to WATERMeDIA + VLC — [Source](https://github.com/NGoedix/VideoPlayer)
- `hackermdch/MediaPlayer` (LGPL-3.0-only, Modrinth) is a Fabric/Forge/NeoForge FFmpeg decode library exposing `VideoDecoder.create(file)`, `decoder.fetch()`, `decoder.frame` → GL buffer plus companion `AudioDecoder` pumped through Minecraft's SoundManager; Windows-x64-only — [Source](https://github.com/hackermdch/MediaPlayer); [Source](https://modrinth.com/mod/mediaplayer)
- `FFmpegLib` (MIT, Forge/NeoForge 1.20.1/1.21.1) manages `ffmpeg.exe` under `config/ffmpeglib/`, runs all decode in separate OS processes ("crash isolation"), and exposes async `FFmpegOrchestrator.extractFrames(video, targetDir, fps)` producing `frame_%04d.png` sequences for GUI/in-game rendering — i.e. pre-transcode-to-frames, no realtime AV clock — [Source](https://www.curseforge.com/minecraft/mc-mods/ffmpeg-lib)
- Minema (offline renderer, MIT) synchronizes "the game engine and OptiFine/shader pipeline from real time to the video recording framerate" and shells out to a user-installed `ffmpeg.exe` for H.264/yuv420p MP4 export — a record-side lockstep pattern, not a watch-side sync protocol — [Source](https://github.com/daipenger/minema)
- `DarkSavci/Minecraft-Video-Player` (Paper 1.19.4) uses JavaCV (`-Djavacpp.platform=...`) on a background thread to hit arbitrary fps (author reports 60 fps on Ryzen 5 5600X), rendering to maps/in-world surfaces — [Source](https://github.com/DarkSavci/Minecraft-Video-Player)
- HLS/DASH in the general ecosystem are plain-HTTP manifest + segment schemes (`.m3u8`/`.mpd` + byte-range segments, no special server component), with ABR in the player (hls.js/dash.js/MSE) — [Source](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Audio_and_video_delivery/Setting_up_adaptive_streaming_media_sources); no MC mod found embedding an HLS/DASH ABR stack in-engine — all browser paths get it free via Chromium.

### Inferences
- The copyable MC-native sync pattern is: server owns wall-clock + authoritative snapshot @ ~20 Hz; clients apply (not discipline) corrections off-thread; packet schema stays fixed-size and versioned. WaterMedia v3's 5-packet, ≤29 B design is the best template even though its code is NC-licensed and cannot be copied verbatim.
- Pre-transcoding to one H.264 + AAC profile (single resolution/fps, faststart MP4) is the de-facto MC approach (Minema export, FFmpegLib frame extraction, CinemaMod server ffmpeg); adaptive HLS/DASH only makes sense if playback moves to MCEF/Chromium, which already implements it.
- Per-client decode (`hackermdch/MediaPlayer`, JavaCV-on-thread) cannot do multi-viewer sync without adding the WaterMedia-style authority layer; frame-sequence fallback (`FFmpegLib`) is inherently sync-free (server pushes frame index).

### Gaps
- WaterMedia v3 `docs/en-us.md` could not be fetched (HTTP 503 at research time), so tick/leader-election/ drift-correction details come from search excerpts, not the primary doc; exact Sync-packet field layout was not verified.
- No MC project found publishing NTP-offset measurement, audio-master vs wall-clock arbitration, or seamless HLS rendition-switch handling in a native GL path.

## Any reusable secure-download patterns (HTTPS-only, allowlists, SSRF/private-IP blocking, hash verification, LRU cache) in MC mods or Java libs?

### Takeaway
The only mature MC secure-fetch reference is CC: Tweaked's HTTP API (explicit private-range + NAT64-prefix blocklist, repeatedly CVE-patched in 2026); WaterMedia/MCEF document HTTPS/platform-resolver behavior but publish no SSRF/hash/LRU-cache code, so hash-pinning + LRU + DNS-rebinding-safe fetch must be assembled from standard Java primitives following the CC: Tweaked checklist.

### Cited Findings
- CC: Tweaked exposes `http.request`/`http.websocket` to in-game Lua and blocks private ranges to prevent SSRF; CVE-2026-47695 shows pre-1.119.0 could be bypassed with NAT64 `64:ff9b::/96`-mapped IPv6 literals reaching internal IPv4 (e.g. `http://[64:ff9b::<hex>]/` → 169.254.169.254 metadata), fixed in 1.119.0 — [Source](https://nvd.nist.gov/vuln/detail/CVE-2026-47695); [Source](https://www.sentinelone.com/vulnerability-database/cve-2026-47695)
- Follow-up CVE-2026-55758 shows the same filter blocked RFC-6052 `64:ff9b::/96` but missed RFC-8215 local-use `64:ff9b:1::/48`, fixed in 1.120.0 via `AddressPredicate` — [Source](https://nvd.nist.gov/vuln/detail/cve-2026-55758)
- SSRF-prevention baseline guidance (validate URL shape, enforce allowlist, resolve-then-check every IP against private/reserved ranges including 10/8, 172.16/12, 192.168/16, 169.254.169.254) matches the CC: Tweaked fix pattern — [Source](https://knowledgelib.io/software/security/ssrf-prevention/2026); DNS-rebinding (resolve-check-then-connect-to-different-IP) is a known bypass of naive check-then-fetch — [Source](https://www.security-threat.com/vulnerability-patterns-web-mitigation-strategies/server-side-request-forgery-ssrf-prevention/dns-rebinding-and-ip-allowlist-bypass)
- Geyser (Bedrock↔Java bridge) had an SSRF via crafted Base64 skin-texture URL causing server-side arbitrary HTTP GET, fixed in 2.9.3 — the MC-specific lesson that even "texture/skin" URLs are SSRF vectors — [Source](https://www.cve.org/CVERecord?id=CVE-2026-42188)
- MCEF downloads CEF/java-cef binaries only over HTTPS from `mcef-download.cinemamod.com` — an HTTPS-only native-fetch precedent, though scoped to its own CDN, not arbitrary media URLs — [Source](https://github.com/CinemaMod/mcef)
- JavaCV's `Loader.cacheResource(URL)` helper downloads-and-caches a remote resource to a local file (used in the Demo for the Haar cascade XML) — a minimal cache primitive, with no documented hash verification or allowlist — [Source](https://github.com/bytedeco/javacv)
- No MC mod or Java AV lib surveyed publishes a combined HTTPS-only + host-allowlist + resolved-IP-block + SHA-256 + LRU-cache media fetcher; WaterMedia v3 docs describe MRL resolution/quality/metadata and hosted/remote storage APIs but expose no fetch-guard source in the surveyed material.

### Inferences
- Copy the CC: Tweaked checklist verbatim for any client-side media fetch that accepts server-supplied URLs: https-only, no userinfo, host allowlist (or at minimum deny-literal-IP + private-suffix deny), resolve ALL A/AAAA records, reject every resolved IP in private/loopback/link-local/CGNAT/ULA/multicast/reserved plus both NAT64 prefixes (`64:ff9b::/96`, `64:ff9b:1::/48`), pin the connected IP (custom Dialer/SSLSocketFactory or `HttpClient` with explicit resolved address + SNI/Host preserved) to close DNS-rebinding, then SHA-256-verify against a manifest before caching.
- LRU/size-capped disk cache with content-addressed filenames (`sha256(url+hash)`) is the missing piece in every MC fetcher found; standard `LinkedHashMap`-LRU or Caffeine + atomic tmp-file-rename is sufficient and avoids partial-file poisoning.
- Treat thumbnail/poster/skin URLs with the same SSRF rigor as video URLs (Geyser lesson).

### Gaps
- I found no reusable single-library "secure MC media downloader" (allowlist + SSRF + hash + LRU) to embed; this must be written (~200 lines) rather than imported.
- WaterMedia's actual URL-validation/cache implementation (if any) was not visible in the surveyed README/excerpts; its platform-resolver auth (cookies for high-quality sources, noted in 3.0.0.16 changelog) was not reviewed for SSRF posture.

## What is the pragmatic recommendation: embed FFmpeg natives vs browser-based playback vs frame-sequence fallback for a first video milestone?

### Takeaway
For mineDisplay's first milestone (Paper map-wall, then MineUI HUD), ship server-side pre-transcode + client frame-sequence/PNG fallback first, spike embedded LGPL FFmpeg decode (JavaCPP presets, single-platform classifiers) second, and defer MCEF/Chromium to a later HD milestone — because only the frame path works everywhere on day one while FFmpeg natives and Chromium each exclude platforms or explode distributable size.

### Cited Findings
- Frame-sequence path is proven by `FFmpegLib.extractFrames(...fps)` → `frame_%04d.png` + async `CompletableFuture` + out-of-process crash isolation (MIT; Forge/NeoForge 1.20.1/1.21.1; `ffmpeg.exe` managed under `config/ffmpeglib/`) — [Source](https://www.curseforge.com/minecraft/mc-mods/ffmpeg-lib)
- Embedded-decode path is proven by `hackermdch/MediaPlayer` (`VideoDecoder.create→fetch→frame→GL`, companion audio via SoundManager) but constrained to Windows-x64-only — illustrating the per-OS native-matrix cost — [Source](https://github.com/hackermdch/MediaPlayer)
- Full-platform FFmpeg via JavaCPP (`javacv-platform` / `ffmpeg-platform` + `-Djavacpp.platform`) and WaterMedia Binaries (Win-x64/Linux-x64+Arm64/Mac-x64+Arm64, no Win-Arm64/Android) show the achievable matrix and the packaging cost: one classifier per OS/arch, full aggregate in the hundreds of MB — [Source](https://github.com/bytedeco/javacv); [Source](https://github.com/WaterMediaTeam/watermedia-v3/blob/main/README.md)
- Browser path (MCEF: Chromium 116, LGPL-2.1, Win/Mac/Linux x64+Arm64, no Android, CEF downloaded at first run from project CDN, antivirus-friction documented) gives HLS/DASH/DRM/codecs for free but adds a ~100 MB+ runtime, a network dependency on a third-party CDN, and GL-interop work — [Source](https://github.com/CinemaMod/mcef)
- VLC path (WaterMedia 2.x: LibVLC backend, per-OS VLC install friction on macOS/Linux, Flatpak/sandboxed installs unsupported) and vlcj-5's dependence on unreleased VLC 4 argue against choosing VLC for a new mod in 2026 — [Source](https://github.com/WaterMediaTeam/watermedia/blob/2.1.x/README.md); [Source](https://github.com/caprica/vlcj/blob/master/README.md)
- JCodec's documented order-of-magnitude slowdown confines pure-Java decode to thumbnails/short-loop fallback, not the primary 1080p path — [Source](https://github.com/jcodec/jcodec)

### Inferences
- Milestone order minimizing risk: (1) server pre-transcodes uploads to H.264/AAC faststart MP4 + PNG sprite/frame sequence at fixed fps/res; client renders frames on maps/HUD with wall-clock pacing and SoundManager/voice audio — works on every Fabric client with zero natives; (2) add optional embedded LGPL-FFmpeg decode behind a capability flag (per-platform classifier downloads, fallback to (1) when absent); (3) evaluate MCEF only when HD/browser-codec breadth justifies the CEF runtime.
- License-safe defaults throughout: ship LGPL FFmpeg builds only (no `-gpl` presets, no x264/x265/native-nonfree), keep WaterMedia-style code as inspiration-only (NC-licensed, cannot be vendored), prefer MIT/Apache/BSD glue (FFmpegLib-MIT, JavaCPP-Apache-2.0, JCodec-FreeBSD, MCEF-LGPL-2.1 as optional dependency).
- The sync authority and SSRF/hash/LRU fetch layer should be built once against the frame-sequence milestone and reused unchanged when FFmpeg decode lands, following WaterMedia's ≤29 B snapshot + 50 ms-tick shape.

### Gaps
- No head-to-head 2026 benchmark (JavaCPP-FFmpeg vs JCodec vs CEF) on MC 1.21.x/Java 21 with maps/HUD upload costs was found; fps/resolution ceilings for the frame-sequence milestone must be measured in-prototype.
- PackHost/CDN + hash-manifest conventions for distributing pre-transcoded profiles are out of scope of this note and need a companion distribution-design decision.
