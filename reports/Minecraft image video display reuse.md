# Borrow map walls, rebuild sync engine

MineDisplay cannot adopt any existing open-source project end to end for its Paper 26.2 plus Fabric-client roadmap, but it can borrow narrowly and build the rest. The vanilla map wall for the first milestone should be self-built on the tiny MIT ImageMaps pattern rather than vendored from the far richer but **GPL-3.0 ImageFrame**, which is the only map stack verified active on 26.x. In-world screen mods split into a dormant Chromium lineage and a popular but legally unreusable VLC lineage, and neither provides server-authoritative sync with vanilla fallback, so only their screen-model and URL-sync ideas transfer. For HUD, MineDisplay's existing MineUI JSON protocol already fills a gap no Java Edition OSS covers, leaving only Fabric's **HudElementRegistry** and an opt-in MCEF fork worth reusing. Video narrows to **LGPL JavaCPP-FFmpeg** with a frame-sequence first milestone because WaterMedia's best sync design is non-commercial licensed and vlcj, LavaPlayer and GStreamer paths are dead ends, which fixes the build order as frames first, embedded decode second, Chromium last.

## Map walls are solved, but only MIT ImageMaps can be borrowed freely

The server-side image-to-map lineage runs ImageOnMap to ImageMaps to ImageFrame, and all three agree on the same irreducible mechanics of splitting images into **128×128 tiles**, quantizing to the vanilla map palette through Bukkit canvas APIs, and persisting one map ID per tile plus placement metadata ([Source](https://github.com/SydMontague/ImageMaps)). ImageMaps is explicit that images split by default into 128×128 sub-images and that the limited map palette visibly shifts colors ingame ([Source](https://github.com/SydMontague/ImageMaps)), while the map format itself is a **16,384-entry 128×128 byte-indexed image** stored as GZip'd NBT `map_<#>.dat` with `idcounts.dat` tracking the latest ID ([Source](https://minecraft.wiki/w/Map_item_format)). Consumer tooling restates the usable palette as **61 flat colors, about 183 staircase colors and 244 with the unobtainable shade**, with Floyd-Steinberg and other dithers as the quality lever ([Source](https://zerohpminecraft.github.io/loominary/)). That palette ceiling means canvas-painted posters are effectively flat-palette plus dither, since the 183-color staircase is a physical height-step build technique rather than something `MapCanvas` painting can invoke, and any HD or full-color promise immediately requires a companion client mod or AV1 stream ([Source](https://github.com/LOOHP/ImageFrame)) ([Source](https://zerohpminecraft.github.io/loominary/)).

Within that shared technical base the reuse verdict turns almost entirely on license and maintenance. ImageFrame is the only full-featured base verified active into 2026 with **native major version 26.2**, per-version NMS modules reaching **V26_3**, animated GIF and TV screens, markers, overlays, MySQL shared maps and an `adminmigrate` importer for older stacks ([Source](https://www.spigotmc.org/resources/imageframe-load-images-on-maps-item-frames-support-gifs-map-markers-survival-friendly.106031/)) ([Source](https://github.com/LOOHP/ImageFrame)). Its cost is **GPL-3.0**, which obligates source disclosure on distribution and rules out vendoring into a differently licensed MineDisplay core ([Source](https://github.com/LOOHP/ImageFrame)). ImageMaps is the opposite trade at **MIT**, Bukkit 1.13 plus with invisible, fixed and glowing frame flags gated on 1.16 and 1.17, a `maps.yml` store, OP-default permissions and a 2025 GitHub-only 1.0.11 fix implying residual life despite only 45 stars and 81 commits ([Source](https://github.com/SydMontague/ImageMaps)). ImageOnMap is stale since **4.2.2 in January 2022** with a documented 1.15 to 1.18 ceiling and should be treated only as a migration source, a role ImageFrame already formalizes ([Source](https://github.com/zDevelopers/ImageOnMap)). The small 2025 to 2026 satellites confirm the niche rather than changing it, with a 7-commit MapImage, a 222-commit GPL Fabric port claiming dynamic NMS color matching and 32-block visibility caching, and a proprietary NeoForge namesake ([Source](https://github.com/tommustbe12com/MapImage)) ([Source](https://github.com/reyhe66243/ImageFrame-Fabric-Port)).

For MineDisplay's map-wall start the pragmatic conclusion is to keep ownership and copy patterns. Bukkit's `MapRenderer` with its contextual per-player flag plus `MapCanvas` clipped `drawImage`, text and pixel access remains the stable compile target on 26.2 Paper and Spigot Javadocs ([Source](https://hub.spigotmc.org/javadocs/bukkit/org/bukkit/map/MapRenderer.html)) ([Source](https://jd.papermc.io/paper/26.2/org/bukkit/map/MapCanvas.html)), and Paper's `MapPalette` with `MapColorCache` plus `Color`-based pixel APIs is where a quality-sensitive implementation would hook custom resize and dither before calling canvas methods ([Source](https://jd.papermc.io/paper/1.21.11/org/bukkit/map/MapPalette.html)). ImageOnMap's quota model of **global plus per-player limits, size caps and an allowlist with bypass permission** against the old **32,767 map-ID ceiling** is load-bearing and should be enforced from day one, since every poster tile otherwise permanently costs one map ID plus one item-frame entity ([Source](https://github.com/zDevelopers/ImageOnMap)). Display entities do not offer a shortcut because filled maps cannot render in `item_display`, which uses a different path from hand-map rendering, so vanilla Phase 1 should stay on **maps in item frames** and use Block, Item and Text Displays only as scalers or labels ([Source](https://minecraft.wiki/w/Display)). Resource-pack `item_model` frames and the ImageFrameClient HD path are separate pack-distribution features, not join-and-see posters, and video must reuse IDs with frame updates rather than minting maps per frame ([Source](https://modrinth.com/mod/imagetitles)) ([Source](https://github.com/LOOHP/ImageFrame)). Two uncertainties persist without weakening the verdict, namely whether any of the three map plugins applies Floyd-Steinberg by default and whether the 26.x map-ID range has moved from the old 32,767 comment to full int IDs.

## World screens impose a Chromium or VLC tax MineDisplay should defer

In-world image and video mods fall into two stable families plus one outlier, and the taxonomy itself dictates the reuse decision. Chromium-texture mods of the WebDisplays lineage composite a per-client offscreen browser to a block-entity texture with click, scroll and JavaScript bridges for free but inherently per-client desync ([Source](https://github.com/CinemaMod/webdisplays)) ([Source](https://github.com/montoyo/mcef)). VLC and FFmpeg-texture mods of the WATERFrAMES, LittleFrames, VideoPlayer and webstreamer lineage decode passively to texture with far less interactivity, while lightweight URL-image frame mods such as PicAxe, Modern Online Picture Frames and Projector skip natives entirely ([Source](https://github.com/SrRapero720/waterframes/blob/1.20.1/README.md)) ([Source](https://github.com/HashiCraft/fabric-projector-mod)). Only WebDisplaysTogether renders on the server and streams video so every viewer sees the identical frame, with headless Chromium on the server plus **VP8/VP9 plus Opus at 30 fps adaptively scaled 360p to 1080p** from server load and per-viewer feedback ([Source](https://github.com/He-Horatio/WebDisplaysTogether)) ([Source](https://github.com/He-Horatio/WebDisplaysTogether/blob/main/README.md)). Jar size is a reliable tell, with **36 to 45 MB jars signaling bundled VLC or FFmpeg natives** and sub-250 KB jars signaling URL-texture or MCEF-dependent mods.

Hard requirements make both heavy families awkward for a Paper plus Fabric project that must degrade to vanilla. The MCEF lineage always needs MCEF plus downloaded Chromium natives around **100 to 200 MB**, desktop Windows, macOS or glibc Linux only with no Android, antivirus friction and a runtime CDN dependency on `mcef-download.cinemamod.com` ([Source](https://github.com/CinemaMod/mcef)). Official MCEF is pinned to **Chromium 116** with its last CurseForge release in **January 2025 for 1.21.4**, while fresher coverage to 26.x comes only from community forks such as the Chromium 122 CCBlueX line and Stonecutter multiversion forks ([Source](https://github.com/CinemaMod/mcef)) ([Source](https://github.mosekj.com/CCBlueX/mcef)) ([Source](https://github.com/meowdding/mcef)). Official WebDisplays itself stops at **1.20.1 Forge from October 2024**, leaving 1.21.1 Fabric and NeoForge to MIT forks and a 26.2 Revived build with only 146 downloads ([Source](https://www.curseforge.com/minecraft/mc-mods/webdisplays/files/4334038)). WebDisplaysTogether is the fresher MIT-own-code exception at **v1.08 in September 2026 for Fabric and NeoForge 1.21.1 plus Forge 1.20.1**, but its server-Chromium install needs system libraries, Xvfb on headless Linux and manual extraction of about **120 MB of java-cef natives** with no macOS server build ([Source](https://www.curseforge.com/minecraft/mc-mods/webdisplaystogether/files/8805117)) ([Source](https://github.com/He-Horatio/WebDisplaysTogether/blob/main/README.md)). The VLC lineage inverts the problem with better 26.x coverage but blocking licenses, since WATERFrAMES at **6.5M downloads updated June 2026 is All Rights Reserved**, WATERMeDIA at **36.1 MB updated July 2026 is Custom**, VideoPlayer at 575K downloads is All Rights Reserved and stale since April 2025, and the Watervision replacement is PolyForm Strict ([Source](https://www.curseforge.com/minecraft/mc-mods/waterframes/files/7129275)) ([Source](https://www.curseforge.com/minecraft/mc-mods/watermedia/files/5921102)) ([Source](https://github.com/NGoedix/VideoPlayer)) ([Source](https://github.com/SrRapero720/watervision)). Safely forkable MIT and CC0 options exist in WebDisplays, WebDisplaysTogether own code, **MIT PicAxe** and **CC0 Projector**, while LGPL LittleFrames, Dream Displays and MCEF are usable as unmodified dependencies with legal review before any static bundling ([Source](https://github.com/He-Horatio/WebDisplaysTogether)) ([Source](https://www.curseforge.com/minecraft/mc-mods/picaxe)) ([Source](https://github.com/HashiCraft/fabric-projector-mod)) ([Source](https://www.curseforge.com/minecraft/mc-mods/dreamdisplays/files/8261946)).

For server-authoritative playback with late-join sync and vanilla fallback almost everything must therefore be rebuilt. WebDisplaysTogether is the only citable server-authoritative reference with clients that only decode and forward input, shared logins, adaptive quality with manual pinning, and config knobs for resolution caps, bitrate, concurrent browsers, idle timeout, blacklist and miniserv quota ([Source](https://github.com/He-Horatio/WebDisplaysTogether/blob/main/README.md)). Everything else syncs only URLs and leaves playback unsynced, with LittleFrames explicitly having each client download the picture itself and WATERFrAMES changelogs showing reconnect time resets and tick-correction jumps rather than true late-join semantics ([Source](https://www.9minecraft.net/little-picture-frames-mod)) ([Source](https://www.curseforge.com/minecraft/mc-mods/waterframes/files/7005589)). Reusable directly are the WebDisplays screen, peripheral, permission and Miniserv data model, the WDT server-render plus speaker-block plus incognito design, Projector's adjacency-scaling plus redstone-gating plus server URL-sync snippet, and VideoPlayer's target, volume and restriction command UX as an idea only ([Source](https://github.com/He-Horatio/WebDisplaysTogether)) ([Source](https://github.com/HashiCraft/fabric-projector-mod)) ([Source](https://github.com/NGoedix/VideoPlayer)). Missing and load-bearing are an authoritative media clock with snapshot plus seek-on-join plus pause-on-empty-room, per-viewer jitter buffers, an audit and consent flow for shared logins, and a DarkSavci-style Paper map-pack fallback with downgraded fps and resolution, all of which must survive restarts behind a new Paper-to-Fabric bridge that no surveyed pair provides ([Source](https://github.com/DarkSavci/Minecraft-Video-Player)). The 26.2 Vulkan migration sharpens the build-versus-borrow call because raw OpenGL video renderers must migrate to Blaze3D, a risk VLC-bundling mods already shipping 26.2 betas absorb faster than the dormant MCEF line ([Source](https://fabricmc.net/2026/06/15/262.html)).

## MineUI already wins the HUD race, reuse only anchors and optional Chromium

No Java Edition OSS matches a server-sent JSON-page HUD protocol, so MineUI's existing declarative system with remote-image support is the asset to protect rather than replace. owo-ui is the only full declarative layout framework with XML hotswap, layout engines and an inspector, yet it renders client-side Screens from packed `Identifier` textures rather than server-driven JSON or remote-URL images ([Source](https://github.com/wisp-forest/owo-lib)) ([Source](https://docs.wispforest.io/owo/ui/)). Its scale at **45.3M Modrinth and 80.7M CurseForge downloads with MIT licensing and builds to 26.2** makes it tempting, but its value overlaps rather than extends a server-driven JSON system and would force a second layout paradigm plus loader lock-in ([Source](https://modrinths.com/mod/ccKDOlHs)) ([Source](https://github.com/wisp-forest/owo-lib)). LibGui is narrower still at **MIT** for logical container screens hung on itemslot grids with on-the-fly drawing and beveled panels, not persistent HUD overlays or free-floating images ([Source](https://github.com/CottonMC/LibGui)). Fabric's Hud API is the correct anchor primitive with `HudElementRegistry` attach-before and after semantics over ordered vanilla layers plus F1 and hide-GUI inheritance, but it takes raw `GuiGraphics` calls and provides no layout engine or image loading ([Source](https://docs.fabricmc.net/develop/rendering/hud)) ([Source](https://github.com/FabricMC/fabric-api/blob/26.2/fabric-rendering-v1/src/client/java/net/fabricmc/fabric/api/client/rendering/v1/hud/VanillaHudElements.java)). Server-side container libraries complete the negative result, with **LGPL-3.0 sgui** and its ServUI port solving no-client-mod vanilla containers without HUD, positioned images or custom rendering ([Source](https://github.com/Patbox/sgui)), and Puzzles Lib proving a false positive as an **MPL-2.0** multi-loader backend that disclaims general-purpose library use ([Source](https://github.com/Fuzss/puzzles-lib)) ([Source](https://www.curseforge.com/minecraft/mc-mods/puzzles-lib)).

Browser embedding for HUD or screen pictures narrows to MCEF as the only viable open-source Chromium embed, with the same cost split seen in world screens. MCEF is **LGPL-2.1 at 149 stars** based on java-cef, CEF and Chromium, and its mod jar is only about **219 KB** because **111 to 168 MB per-platform CEF natives** download on first run with progress and hash checks ([Source](https://github.com/CinemaMod/mcef)) ([Source](https://www.curseforge.com/minecraft/mc-mods/mcef/files/all)) ([Source](https://github.com/guusdk/java-cef/releases)) ([Source](https://github.com/Keksuccino/mcef_resources/releases)). That split plus glibc, X11 and antivirus friction is the dominant ops cost, and upstream staleness means pinning to a maintained fork plus mirrored natives rather than CinemaMod upstream ([Source](https://github.com/CinemaMod/mcef)). Per-client WebDisplays on blocks and server-rendered WebDisplaysTogether show the two browser-to-texture shapes, while the far more popular **6.5M-download WATERFrAMES** uses VLC and WATERMeDIA rather than Chromium and is All Rights Reserved despite URL, local-file, rotation, transparency, brightness and audio-distance features that read like a requirements list ([Source](https://github.com/CinemaMod/webdisplays)) ([Source](https://github.com/He-Horatio/WebDisplaysTogether/blob/main/README.md)) ([Source](https://www.curseforge.com/minecraft/mc-mods/waterframes/files/7129275)). No mature JxBrowser or Ultralight Minecraft integration surfaced, and whether MCEF can render directly into a Fabric `HudElement` versus only Screens and block entities remains unverified without deeper java-cef Javadoc work.

The server-driven protocol search reinforces keeping MineUI custom. sgui covers vanilla containers, WebDisplays miniserv and URL sync plus WDT server-rendered video cover browser content rather than HUD JSON, and Bedrock's `ActionFormData`, `MessageFormData` and `ModalFormData` plus Observable-backed DDUI custom forms are Bedrock-scripting only ([Source](https://github.com/Patbox/sgui)) ([Source](https://github.com/He-Horatio/WebDisplaysTogether/blob/main/README.md)) ([Source](https://learn.microsoft.com/en-us/minecraft/creator/documents/scripting/intro-to-ddui)). The Java gap between lowest-common-denominator containers and full-client-mod rendering is exactly what a plugin-message JSON protocol with vanilla fallback fills, and nothing reusable was found in between. Worth reusing is therefore minimal and precise, namely Fabric `HudElementRegistry` and `VanillaHudElements` for anchoring without fighting draw order while avoiding the deprecated `HudRenderCallback` path ([Source](https://docs.fabricmc.net/develop/rendering/hud)) ([Source](https://github.com/FabricMC/fabric-docs/blob/main/versions/1.21.8/develop/rendering/hud.md)), plus an LGPL-compliant external MCEF dependency behind config and platform checks where MCEF's own rule allows a different license when its source is neither modified nor included ([Source](https://github.com/CinemaMod/mcef)). Video and HTML must stay opt-in and isolated so static-image HUDs remain on the lightweight `NativeImage` path, with Chromium commit pinned, natives mirrored, download progress surfaced, and URL-whitelist and permission patterns borrowed as design references from WDT and WATERFrAMES without copying ARR code ([Source](https://github.com/He-Horatio/WebDisplaysTogether/blob/main/README.md)). Adopting owo-ui, LibGui, Puzzles Lib or WATERFrAMES as foundations would add weight without closing the JSON-protocol, layout, async remote-image cache or Paper-API gaps.

## Video decode narrows to LGPL FFmpeg while sync and fetching must be rebuilt

Only two decode paths are realistically embeddable in a Java 21 or 25 Fabric mod, and only one suits primary playback. JavaCPP and FFmpeg presets via JavaCV or WaterMedia-style direct preset use provide maintained natives across desktop OSes with per-platform jars selectable by `-Djavacpp.platform`, currently around **FFmpeg 8.1.x with JavaCPP 1.5.14** ([Source](https://github.com/bytedeco/javacv)) ([Source](https://github.com/bytedeco/javacpp-presets/blob/master/ffmpeg/README.md)). The safe redistributable default is the **LGPL `ffmpeg-platform` build without `--enable-gpl`, x264 or x265**, since most FFmpeg files are **LGPL-2.1-or-later** and enabling GPL libraries or nonfree combos flips the binary to GPL or unredistributable ([Source](https://github.com/FFmpeg/FFmpeg/blob/master/LICENSE.md)) ([Source](https://www.ffmpeg.org/legal.html)). Pure-Java **FreeBSD-licensed JCodec** with H.264 main-profile decode, baseline encode, VP8 I-frames only and MP4, MKV and MPEG demux is the legitimate zero-native fallback, but its documented **order-of-magnitude slowdown** versus native confines it to thumbnails and short loops rather than 1080p60 ([Source](https://github.com/jcodec/jcodec)). The exclusions are firm, with **GPL-3.0 vlcj-5 pinned to unreleased VLC 4**, audio-only LavaPlayer that by design emits Opus frames for Discord bots, deprecated Xuggler, **AGPL-3.0** Humble Video on a stale JDK-1.6-era matrix, and GStreamer Java bindings that need a system install with a 2021-era release line ([Source](https://github.com/caprica/vlcj/blob/master/README.md)) ([Source](https://github.com/lavalink-devs/lavaplayer/blob/main/README.md)) ([Source](https://github.com/artclarke/xuggle-xuggler)) ([Source](https://github.com/artclarke/humble-video)) ([Source](https://github.com/gstreamer-java/gst1-java-core)). MCEF's Chromium 116 path gives HLS, DASH and broad codecs for free but repeats the 100 MB plus runtime plus CDN cost, while WaterMedia v3 shows the achievable FFmpeg matrix at **Windows x64, Linux x64 plus Arm64 and macOS x64 plus Arm64 with no Windows Arm64 or Android** on an **LGPL-3.0 FFmpeg 8.1.2 build without GPL flags** ([Source](https://github.com/CinemaMod/mcef)) ([Source](https://github.com/WaterMediaTeam/watermedia-v3/blob/main/README.md)).

No Minecraft project implements NTP-style discipline or in-engine HLS and DASH adaptive switching, so the reusable sync shape is WaterMedia v3's without its code. WaterMedia v3 pairs `TxMediaPlayer` and `FFMediaPlayer` with a headless wall-clock `ServerMediaPlayer` as server-side time authority, resolves sources through MRL with quality variants, and transports authority in **small fixed-size big-endian records of at most 29 bytes** applied off the game thread on its own 50 ms tick ([Source](https://github.com/WaterMediaTeam/watermedia-v3)) ([Source](https://github.com/WaterMediaTeam/watermedia-v3/blob/main/README.md)). Browser mods delegate sync to Chromium or VLC, frame-sequence libraries avoid sync entirely, and general HLS and DASH remain plain-HTTP manifests with player-side adaptation that only comes for free inside Chromium ([Source](https://github.com/CinemaMod/CinemaMod)) ([Source](https://github.com/NGoedix/VideoPlayer)) ([Source](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Audio_and_video_delivery/Setting_up_adaptive_streaming_media_sources)). The copyable Minecraft-native pattern is therefore server-owned wall clock with roughly 20 Hz authoritative snapshots, client-side apply rather than discipline off-thread, fixed-size versioned packets, single-profile H.264 plus AAC pre-transcode with faststart, and per-client MRL or platform resolvers. Directly proven endpoints bound the choice, with **MIT FFmpegLib** extracting `frame_%04d.png` sequences out of process for crash isolation and `hackermdch MediaPlayer` proving `VideoDecoder.create` to fetch to GL with SoundManager audio but only on **Windows x64** ([Source](https://www.curseforge.com/minecraft/mc-mods/ffmpeg-lib)) ([Source](https://github.com/hackermdch/MediaPlayer)) ([Source](https://modrinth.com/mod/mediaplayer)). Minema's record-side lockstep and DarkSavci's JavaCV-on-thread 60 fps report are useful existence proofs rather than watch-side sync protocols ([Source](https://github.com/daipenger/minema)) ([Source](https://github.com/DarkSavci/Minecraft-Video-Player)). WaterMedia v3's code itself cannot be vendored because **v2.x is Polyform Strict non-commercial and v3 is Defensive Public Source non-commercial**, so its packet shape is inspiration only ([Source](https://github.com/WaterMediaTeam/watermedia/blob/2.1.x/README.md)) ([Source](https://github.com/WaterMediaTeam/watermedia-v3/blob/main/README.md)).

Secure fetching is the second must-build layer because no surveyed media fetcher combines the needed guards. CC: Tweaked's HTTP API is the only mature Minecraft secure-fetch reference with an explicit private-range plus NAT64 blocklist, twice CVE-patched in 2026 for **`64:ff9b::/96` and `64:ff9b:1::/48` bypasses to 169.254.169.254 metadata** ([Source](https://nvd.nist.gov/vuln/detail/CVE-2026-47695)) ([Source](https://nvd.nist.gov/vuln/detail/cve-2026-55758)). Geyser's Base64 skin-texture SSRF fix proves even poster and thumbnail URLs are vectors ([Source](https://www.cve.org/CVERecord?id=CVE-2026-42188)), while MCEF's HTTPS-only CDN fetch and JavaCV's `Loader.cacheResource` show only fragments of the full HTTPS-only plus allowlist plus resolved-IP blocking plus hash plus LRU shape ([Source](https://github.com/CinemaMod/mcef)) ([Source](https://github.com/bytedeco/javacv)). The checklist to copy verbatim is HTTPS only with no userinfo, host allowlist or at minimum literal-IP and private-suffix denial, resolution of all A and AAAA records with rejection of private, loopback, link-local, CGNAT, ULA, multicast, reserved and both NAT64 prefixes, IP pinning at connect to close DNS rebinding, and SHA-256 verification against a manifest before content-addressed LRU caching ([Source](https://knowledgelib.io/software/security/ssrf-prevention/2026)). That plus the sync authority should be built once against the frame-sequence milestone and reused unchanged when embedded FFmpeg lands. The pragmatic milestone order is therefore server pre-transcode to faststart MP4 plus PNG sprites at fixed fps and resolution with wall-clock pacing for maps and HUD first, optional embedded LGPL-FFmpeg decode behind a capability flag with single-platform classifiers second, and MCEF only when HD or browser-codec breadth justifies the runtime, keeping VLC paths out on license and install-friction grounds ([Source](https://www.curseforge.com/minecraft/mc-mods/ffmpeg-lib)) ([Source](https://github.com/jcodec/jcodec)) ([Source](https://github.com/caprica/vlcj/blob/master/README.md)).

## Conclusion

The efficient strategy is to treat map tiling, HUD anchoring and FFmpeg preset mechanics as borrowed commodities while treating authoritative sync, secure fetch and the Paper-to-Fabric media bridge as MineDisplay-owned inventions. That split respects the actual license boundaries found, where MIT, LGPL and Apache pieces permit reuse but ARR, Custom and non-commercial pieces punish vendoring, and it sequences risk so every milestone ships on vanilla before paying any native or Chromium tax. The remaining unknowns that should gate later milestones are measured rather than researched, namely frame-sequence fps ceilings on maps and HUD, per-platform FFmpeg classifier sizes, CEF offscreen-to-texture cost under Vulkan, and CPU per server-rendered screen.
